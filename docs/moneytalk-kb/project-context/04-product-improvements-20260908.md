# 제품 사용성 개선 검토

이 문서는 현재 구현과 선택 이유를 설명한다. 사용자의 재방문율 상승, 수익 개선, 운영 데이터에서의 예상 정확도를 측정한 보고서가 아니다. 13개 화면의 책임 분리는 [구조 감사](03-screen-function-architecture-audit.md), 기능별 구현은 [Home](../home/README.md), [History](../history/README.md), [거래 변경](../transaction-mutation/01-feature-flow.md)을 따른다.

## 문제와 선택

MoneyTalk에는 이미 문자 자동 기록, 월별 목록/달력, 누적 차트, 예산, 카테고리 필터, 거래처 규칙, 원문 확인과 AI 조회가 있다. 이번 코드 감사에서는 기능 개수보다 기록을 확인한 뒤 다음 행동으로 이어지는 흐름을 보완했다. 기록의 정확성 개선과 사용성 개선은 별개이며 새 카드가 문자 누락/중복을 해결했다고 보지 않는다.

| 사용자 불편 | 이번 구현 | 기대 효용과 확인 범위 |
|---|---|---|
| 거래를 정리할 작업을 빠르게 고르고 싶다 | 4개 거래 목록의 롱클릭 수정/삭제 메뉴 | 거래명과 수정/삭제만 보여준다. 수정은 기존 상세 편집을 열고, 삭제는 별도 확인 후 한 건을 처리한다. |
| 월 합계를 봐도 남은 기간을 어떻게 조절할지 직접 계산해야 한다 | 무료 로컬 소비 브리핑 | 남은/초과 예산, 오늘 포함 남은 일수와 하루 참고액, 최근 두 주의 기록 차이를 즉시 제공한다. |
| 가계부가 과거 기록만 보여준다 | 근거가 충분한 고정 지출의 다음 결제 예상 | 가까운 지출을 확인하고 최신 실제 거래로 이동한다. 확정 일정이나 실제 계좌 가용액으로 표현하지 않는다. |
| 수입 보기에서 검색해도 수입 내역을 찾지 못한다 | 지출·수입 검색 연결 | 기존 수입 DAO의 설명/유형/출처/카테고리/메모 검색을 History 결과에 포함한다. |

## 공식 제품 자료와 MoneyTalk의 차이

확인일은 2026-09-08이다. 공식 제품/고객센터 문서를 확인했으며 경쟁 앱 계정의 실제 사용 데이터를 조사하지 않았다. 오래된 도움말은 기능의 존재 근거이며 최신 기기의 화면 배치를 보장하지 않는다.

| 제품 | 공식 자료에서 확인한 기능 | 이번에 참고한 원리와 차이 |
|---|---|---|
| 편한가계부 / Realbyte | 주·월 합계, 예산, 상세 필터와 달력. [공식 제품 페이지](https://www.realbyteapps.com/), [공식 검색 도움말](https://help.realbyteapps.com/hc/en-us/articles/360043325753-How-to-search) | 자주 하는 확인과 정리를 짧게 연결한다. MoneyTalk에 이미 있는 차트/필터를 다시 만들지 않고 기존 거래 행에서 직접 수정한다. 검색 도움말은 2023년 갱신 표시다. |
| 뱅크샐러드 | 남은 예산과 남은 기간을 활용한 하루 권장 예산, 고정지출 관리. [공식 가계부 설명서](https://help.banksalad.com/2d2116e2-39f6-800b-84d4-cd26a7ba7dc4) | 통계를 행동에 참고할 수 있는 숫자로 만든다. MoneyTalk는 은행 잔액과 미기록 지출을 모두 알지 못하므로 ‘하루 참고액’으로 표시한다. 뱅크샐러드의 예산 제외와 MoneyTalk의 통계 제외는 같은 정책으로 간주하지 않는다. |
| YNAB | 가져온 거래의 승인·분류·매칭과 예정 거래. [공식 거래 검토/매칭](https://support.ynab.com/en_us/approving-and-matching-transactions-a-guide-ByYNZaQ1i), [공식 예정 거래](https://support.ynab.com/scheduled-transactions-a-guide-BygrAIFA9) | 자동 기록 후 짧은 정리, 가까운 지출 확인을 참고한다. MoneyTalk에는 승인 상태/지출 납기일 모델이 없으므로 승인 체계를 만들지 않고 단건 수정과 읽기 전용 예상만 제공한다. |

선택 기준은 외부 API 비용·새 라이브러리·DB 스키마 변경 없이 기존 데이터에서 효용을 얻는 것이었다. 반복 거래를 미래 `ExpenseEntity`로 자동 적재하는 기능은 SMS 실제 결제와 중복될 수 있어 도입하지 않았다. 편한가계부의 사용자 지정 반복 입력과 현재 MoneyTalk의 기록 기반 예상은 서로 다른 기능이다. [공식 반복 입력 도움말](https://help.realbyteapps.com/hc/en-us/articles/360043328193-How-to-set-up-a-repeat-schedule-installment)

## 로컬 소비 브리핑

`HomeViewModel`이 기존 카드/문자 가시성 필터와 통계 포함 조건을 적용한 뒤 `SpendingBriefingCalculator`에 전달한다. 모델/계산/예산 UI/주간 UI는 `feature/home/briefing/`에서 분리한다.

- 사용자 회계월의 전체 예산에서 해당 월 기록 지출을 뺀다. 월 지출에는 기존 홈과 같이 미래일 수동 기록도 포함한다. 수입·환불을 계산기가 임의로 차감하지 않는다.
- 오늘을 포함해 회계월 종료일까지 남은 날짜를 세고, 비음수 잔여 예산을 날짜 수로 나눈 원 단위 내림을 참고액으로 표시한다. 예산 초과 시 초과 금액을 표시하고 참고액은 숨긴다. 미설정 또는 과거/미래 월도 참고액을 숨긴다.
- 현재 회계월은 오늘 포함 최근 7개 날짜와 직전 7개 날짜를 비교하며 현재 시각 이후 기록은 제외한다. 과거 월은 마지막 날짜 기준으로 비교한다. 합계는 `Long`, 날짜 경계는 `LocalDate`/`ZoneId`다.
- 두 주의 차이가 가장 큰 양수 카테고리를 보여주고 현재 선택 회계월의 카테고리 내역을 연다. 이 버튼은 주간 범위 전용 근거 목록이 아니다.
- 항상 ‘기록된 내역 기준’을 표시하고 권한 없음/부분 수집을 추가 안내한다. 감소를 실제 절약으로 단정하지 않는다. 예산 미설정 안내는 현재 `설정 > 월 예산 설정` 경로를 알려준다.

홈의 기존 자동 Gemini 인사이트 호출을 제거했다. 남아 있는 `generateHomeInsight()`와 `AiInsightCard` 선언은 현재 홈 실행 경로에서 호출하지 않는다. 새 계산에는 AI/광고/크레딧이 없지만 문자 분류나 사용자가 실행하는 AI 상담까지 비용이 없어진 것은 아니다.

## 고정 지출 예상

`feature/home/recurring/RecurringExpenseForecastCalculator`는 보이는 과거 거래를 거래처+카드로 묶는다. 비고정·통계 제외·이체도 먼저 그룹에 포함하므로 최근 설정 변경이나 같은 달 중복 청구가 보이지 않게 걸러지는 오류를 피한다.

- 최신 최대 3개 관측 월에서 월마다 1건이고 연속 최소 2개월이어야 한다. 모두 고정, 통계 포함, 일반 지출, 양수 동일 금액, 같은 카테고리여야 한다. 일자 차이는 3일 이내 또는 모두 월말이어야 한다.
- 최신 관측은 이번 달 또는 직전 달이어야 한다. 마지막 실제 결제의 다음 월만 예상하며 짧은 달은 말일로 보정한다. 이미 지난 예상일을 다음 달로 계속 넘기지 않는다.
- 오늘부터 30일 안의 후보를 처음 3개와 전체 보기 시트에 표시한다. 후보가 없으면 카드를 숨긴다. 입력이 적은 사용자에게 예상을 억지로 채우지 않는다.
- `sourceExpenseId`는 최신 실제 기록이며 누르면 그 거래를 연다. 미래 거래 저장, 예산 차감, 예약 알림, 고정 표시 자동 변경은 하지 않는다.
- 계산기는 6개월을 한도로 보지만 Home은 현재 달력 월 3개월 전부터 조회한다. 최신 연속 2~3개월 판정에 필요한 범위를 제공하며 과거 월 페이지에는 예상 카드를 표시하지 않는다.

두 번의 관측이 실제 구독 계약을 증명하지는 않는다. 해지·휴일·변동 요금·문자 누락을 모두 알 수 없으므로 예상 정확도는 실제 사용으로 확인할 후속 지표다.

## 단건 수정과 검색의 저장 경계

`TransactionCardCompose.onLongClick` → 화면별 `TransactionQuickActionViewModel` → `TransactionQuickActionDialog`로 연결한다. Home 오늘 거래, History, Category Detail, Transaction Detail List가 같은 동작을 사용한다.

- 지출/수입 유형과 ID를 함께 사용한다. 작은 중앙 메뉴는 거래명·닫기 X·수정/삭제만 표시하며 카테고리·고정·통계 제외 입력과 저장 버튼을 두지 않는다.
- `수정`은 유형과 ID를 기존 `TransactionEditActivity`로 전달한다. 카테고리·고정·통계 제외·금액·메모·원문·일괄 적용은 기존 상세 편집의 계약을 따른다.
- 메뉴 닫기는 데이터를 바꾸지 않는다. `삭제`는 거래명·금액을 확인하는 별도 dialog를 거쳐 `TransactionQuickActionService.delete()`가 최신 행을 삭제하고 성공한 원본 SMS ID를 삭제 추적에 남긴다.
- 삭제 중 중복 동작을 막고, 연속 다른 거래 열기에서는 이전 로드가 최신 메뉴를 덮어쓰지 않게 한다. 삭제 후 기존 `TRANSACTION_ADDED`로 관련 화면을 갱신한다.
- History는 전체 기간 지출/수입 검색 결과를 현재 페이지에 보여준다. 지출과 수입 모두 SMS 제외를 적용한다. 수입은 카테고리·고정 조건과 수입 표시 여부를 반영하고, 카드 선택 시 수입을 제외한다. 취소된 검색이 검색 종료 후 월 목록을 덮어쓰지 않게 Job을 관리한다.

## 검증 상태와 확인할 효과

사용자의 정보 과다 피드백으로 메뉴를 거래명·닫기·수정/삭제로 축소한 뒤 `assembleDebug`, `assembleDebugAndroidTest`가 성공했다. 지출·수입 UI 검사 2개가 통과했고 수동 자료 생성 1개는 제외했다. 수정 화면의 유형별 ID 전달, 닫기·수정 진입 시 무변경, 삭제 취소·확정과 같은 ID의 반대 유형 보존을 확인했다. 2076×2152 폴더블과 1080×2400 휴대폰·글자 1.5배에서 간단 메뉴를 확인했다. 로그와 화면은 `artifacts/compact-transaction-menu-20260908/`에 있다. 실기기는 미연결이므로 이번 수정은 에뮬레이터에만 설치했다.

아래 빌드·화면 검증은 입력 필드가 있던 이전 구현의 이력이다.

2026-09-08 중앙 모달 전환 전 제품 개선 소스에서 `assembleDebug`, `assembleRelease`, `assembleDebugAndroidTest`, `testDebugUnitTest`가 성공했다. JVM 388개 통과, Android 에뮬레이터 자동 검사 88개 통과(수동 QA 자료 생성 1개는 기본 실행에서 제외)했다. 별도 수동 QA 자료 생성은 명시적으로 실행했다.

같은 날 중앙 모달 전환 후 `assembleDebug`, `assembleRelease`, `assembleDebugAndroidTest`를 다시 확인했다. `TransactionQuickActionUiTest`의 지출·수입 흐름 2개가 통과했고 수동 자료 생성 1개는 제외했다. 닫기 X의 미저장 취소를 기존 검사에 추가했으며, 일반/폴더블 너비·글자 1.5배·다크 모드, 삭제 취소·뒤로가기·바깥 터치 닫기를 화면에서 확인했다. 이 추가 검증의 로그와 화면은 `artifacts/quick-action-modal-20260908/`에 있다. 당시 실기기는 미연결 상태였다.

- 대상은 Android 16 `MoneyTalk_Sms_QA_API_36` (`emulator-5556`)이다. 실기기는 연결되지 않았고 합성 거래만 사용했다.
- 기본 폴더블 해상도 2076×2152와 일반 휴대폰 너비 1080×2400, 글자 배율 1.5에서 거래 팝업을 확인했다.
- 카테고리/고정/통계 제외 저장, 지출 12,340원 제외 후 월·일 합계 0원, 수입 카테고리 배지, 삭제 취소·확정과 같은 숫자 ID의 다른 유형 거래 보존을 확인했다.
- 예산 100만원·기록 지출 62,500원에서 남은 937,500원, 오늘 포함 24일, 하루 참고액 39,062원을 확인했다. 예산을 5만원으로 바꾸면 12,500원 초과와 참고액 숨김을 확인하고 QA 예산을 복구했다.
- 과거 월은 마지막 7일 기준이며 미래 일수/하루 참고액/고정 예상이 표시되지 않았다. 예상 14,500원 항목은 9월 12일로 표시되고 누르면 근거인 8월 12일 실제 거래가 열렸다.
- 로그는 로컬 `artifacts/overnight-improvements-20260908/`의 `build-final-reviewed.log`, `regression-instrumented.log`, 화면 XML/PNG에 보관한다. 권한/coverage의 모든 조합과 실제 서비스 유지율은 별도 검증 범위다.

| 브리핑 UI | 미설정·초과·과거 월·부분 수집/권한 없음·큰 글자, 카테고리와 실제 예상 근거 도착 |
| 제품 효과 | 사용자가 참고액과 예상을 이해하는지, 단건 정리 왕복이 줄어드는지, 일주일 뒤 반복해서 확인하는지. 아직 측정하지 않음 |

기능 확인을 위한 원문·거래처·금액의 추가 Analytics 전송은 도입하지 않았다. 실제 사용자 유지율·광고 수익·예측 적중률 개선은 별도 관찰 없이 수치로 주장하지 않는다.

## 별도 후속: 합계 정의와 운영 확인

아래는 이번에 구현한 기능의 완료 내역이 아니다. 데이터 의미나 운영 콘솔 확인이 필요한 경계를 기록한다.

| 후속 | 확인된 근거/범위 | 필요한 확인 |
|---|---|---|
| 수입 합계 정의 정렬 | 코드상 `ExpenseEntity(TRANSFER, DEPOSIT)` 50 + `IncomeEntity` 100이면 History의 `filteredIncomeTotal`은 150, Home의 IncomeRepository 월 수입과 History `dailyIncomeTotals`는 100이 될 수 있다. 실기기 금액 불일치 측정이 아니라 코드 경계 사례다. | 수입·유입·이체를 화면에서 어떤 의미로 표시할지 먼저 정하고 동일 fixture로 월/일/필터 합계를 대조한다. 임의로 모두 150 또는 100으로 통일하지 않는다. |
| 기존 금액 집계 범위 | 신규 브리핑/예상은 `Long`이지만 기존 일부 화면 월 합계는 `Int`다. | 큰 거래 합산의 표시 일관성은 별도 범위로 점검한다. 이번 기능에서 DB 금액 타입을 변경하지 않았다. |
| 개인정보/수집 정책 | 문자 원문·학습 표본·진단 데이터 경로와 사용자 고지/동의의 정합성은 로컬 제품 UI만으로 결론 낼 수 없다. | 현재 RTDB/로그/보관·삭제 정책과 배포 고지를 별도 확인한다. 이 작업에서 외부 표본 수집 범위를 확대하지 않았다. |
| 과금·광고 지급 | 사용자가 광고 수익을 받은 적 없다고 보고했다. 새 홈 기능은 자동 AI 요청을 줄이지만 과거 청구 원인과 지급 상태를 증명하지 않는다. | 월별 실제 청구 프로젝트/서비스, AdMob 추정 수익·확정 수익·지급 상태를 구분해 콘솔 이력으로 확인한다. 기능 구현을 수익성 검증으로 취급하지 않는다. |
